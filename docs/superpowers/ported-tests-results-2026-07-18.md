## Observed recurring patterns (for a future triage session — NOT investigated this task)

The 207 non-FPU failures cluster strongly around a small number of themes, suggesting a
handful of root causes could explain a large fraction of them:

1. **Memory-indirect addressing (`*_memind_*`)** across nearly every instruction family
   that supports it: ADD/AND/ANDI/bitfield (BFCHG/BFCLR/BFEXTU/BFINS/BFSET)/MOVE/PACK/
   UNPK. Almost all HANG rather than FAIL, suggesting the µcode engine either never
   enters or deadlocks for many memory-indirect shapes beyond the ones Task 4 already
   fixed (task #147 fixed exactly one memory-indirect crack; there appear to be several
   more unfixed sibling shapes).
2. **PC-relative indexed jump/call (`jmp_pc_*`, `jsr_*_pc_*`, movement/`*_pc_indexed_*`)**
   — near-universal HANG for JMP/JSR through PC-relative indexed EAs; several MOVE/CMP/
   MOVEA "pc_indexed"/"pc_xn_src" variants FAIL rather than hang.
3. **Scc-on-memory (`scc_*`)** — every `scc_*` test in batch 6 (abs_long, d16_an_disp,

## Concerns

1. **The 207 non-FPU failures represent a substantial, real gap** between this project's
   integer-68040 ISA claim and actual directed-test conformance — nearly 30% of the
   non-FPU corpus fails. This is expected/appropriate to surface via this task (which was
   explicitly scoped to "run and record, don't fix"), but it means the "ISA completion
   roadmap" memory's "INTEGER 68040 ISA COMPLETE" framing needs qualification: complete in
   the sense of "every opcode has *some* decode/execute path," not "every opcode+addressing-
   mode combination is verified correct." A future session doing root-cause work should
   start with the memory-indirect and PC-relative-indexed clusters (highest test counts,
   clearest single-cause signature) before the more heterogeneous exception/RTE cluster.
2. **Wall-clock cost.** The full sweep took ~74 minutes end-to-end with no parallelism
   across batches (sequential by design, one JVM/Verilator compile per batch, per the
   established `sweep.sh` discipline this project uses to avoid JVM OOM — see the
   `lockstep-jvm-oom-hang` memory finding). A future re-run after fixes land will cost
   similarly unless batches are parallelized across separate JVMs/cores, which was not
   attempted here (out of this task's scope) and would need to be weighed against the
   `machine-resource-budget` memory's 29GB/2-concurrent-heavy-JVM guidance.
3. **`movea_w_pc_brief_scale`'s assemble/toolchain error** is a different failure class
   than everything else (a vendored `.s` source that doesn't assemble under
   `m68k-linux-gnu-as -m68040`, likely a corpus-vendoring artifact or genuinely invalid
   asm in the original m68k-ooo corpus) — flagged distinctly so a future session doesn't
   waste time treating it as an RTL bug.
4. No fixes were attempted in this task, per its explicit scope. All 242 failures
   (207 non-FPU + 35 FPU + 1 toolchain, with 1 of the 207 being the already-known
   `aline_triple_nested_dbf_storm`) are recorded for future work, not resolved.
